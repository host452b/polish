# 决策与生命周期视角

按实际目标和阶段选用视角。这些是生成问题的提示，不是每个项目都必须完成的清单，也不能证明同行都采用了某项实践。

| 场景 | 寻找容易被遗漏的边界 | 能改变决策的证据示例 |
| --- | --- | --- |
| 架构 | 假设的负载与一致性；故障传播；状态归属；组织维护能力 | 用真实访问模式试验故障、并发或降级，而非仅看理想吞吐 |
| 技术选型 | 当前版本能力；运行总成本；升级、迁移与退出成本；许可证约束 | 代表性工作负载、数据导出再导入、维护工作量；来源及适用版本 |
| 已实施改造 | 新旧版本并存；旧数据读取；迁移中断；不可逆状态；回滚与前向恢复 | 在隔离副本上完成升级、产生新数据、再恢复服务，验证数据语义 |
| 上线和长期运行 | 发现故障所需信号；恢复责任；容量与费用边界；数据生命周期 | 能发现什么故障、谁处理、怎样恢复、如何确认用户操作仍正确 |
| 原型和小规模试用 | 首次使用是否理解；实际使用场景；收集反馈的成本 | 少量代表用户独立完成核心任务；优先可观察的学习结果 |
| 同行对照 | 对方规模、用户、团队和约束是否相似；实践解决什么问题 | 一手公开工程文档或案例中的明确条件；当前项目是否存在同一机制 |
| 收益与简化 | 已有数据、工具和流程能否复用；能否删除或延后投入 | 当前重复劳动、耗时或成本；已有资产是否覆盖同一目标；小规模对照结果 |

## 按变化追踪上线后的首次情境

只选择最相关的情境，串起“变更 → 新边界 → 触发 → 可观测后果”。分别标记本次新增、本次放大、既有但无关或证据不足。

| 情境 | 要核验的边界 |
| --- | --- |
| 新旧版本共存或回退 | 请求、协议和新写入数据能否跨版本工作 |
| 超时、重试或重放 | 下游已完成副作用但响应丢失时，重试是否重复执行 |
| 依赖变慢或断开 | 等待、队列与连接池是否堆积；如何限制影响并恢复 |
| 缓存失效或规模扩大 | 集中回源、热点和流量分布是否推翻容量假设 |
| 恢复、值班与交接 | 谁发现用户症状，谁有权限处置，恢复如何按业务结果确认 |
| 长期运行、升级与退出 | 数据、费用、质量与依赖随时间变化后，原判断是否仍成立 |

演练与故障注入是验证建议，执行遵循任务权限；仅分析任务不因此获准操作真实系统。

## 连接已有知识与同行能力

历史检索除了找遗漏，还要找“已解决、已接受、有后续更新”的反证。用户熟悉术语不等于掌握全部边界；没有说过术语也不证明缺少能力。

有现成样本时，可核验是否能复用为评测材料；有真实日志时，可检查其能否回答容量或耗时问题。需有实际材料支持连接，并测量复用收益；不要因为能新增系统就推荐新增。

同行对照按“案例约束 → 采用机制 → 可证实的结果 → 本项目同类约束 → 已有等价能力”核验。有现成服务、脚本或定期人工流程满足目标时，不要求引入同名组件。写明何种信号才值得投入、谁承担维护成本；缺少可比资料则保留为调研方向。

## 贯穿示例：代码回退与数据恢复

假设材料明确说：服务已改成写 V2 数据，CI 只验证新程序读 V2，发布文档的回滚动作只有换回旧镜像。

可支持的发现是：“换回旧镜像还不能证明能恢复服务。”不能从这些材料直接断言“旧版一定读不了 V2”或“团队从来没考虑回滚”。

最小验证：在隔离数据副本上升级、写入代表性 V2 数据，再按既定回滚步骤启动旧版本并执行关键读写。通过标准是关键操作语义正确且数据完整；恢复时间和可接受丢失量使用项目已有目标，没有则明确待定。

通过：降低该边界的不确定性，仍保留未覆盖数据类型和负载限制。失败：修订恢复路线，例如兼容阶段或前向修复；备份恢复只有在覆盖新写入损失要求时才可作为方案。历史演练必须核对版本、数据格式和恢复目标，不能证明改造后仍可恢复。
