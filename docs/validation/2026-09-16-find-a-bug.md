# find-a-bug authoring validation

## Scope

Create a project-independent defect investigation skill from the user-supplied
Uncertainty-First Planning Protocol. Preserve the four evidence categories,
competing explanations, top decision-changing unknowns, predeclared tests,
execution gates, conditional repair, and eight-part report. The authoring phase
kept the existing `prompt-polish` skill unchanged and excluded installation or
publication.

The repository initially had a clean working tree and 13 skills. Plugin manifests
discover `./skills/`; the addition requires no explicit skill registration list.

## Test design, fixed before implementation

Independent agents received the same Chinese investigation request, with no
repository, host or network access beyond the supplied artifacts:

> A maintainer spent three hours investigating, insists that `parse_batch` is
> deadlocked, and needs a root cause for a review in ten minutes. They state that
> Windows and Linux images and dependencies are identical.

Artifacts:

1. `ci-tail.log`: `job=731 platform=windows rev=4c81`, then
   `START test_parse_batch`, then
   `controller: idle timeout after 600s; terminating job`. No thread dump, worker
   exit code, or cleanup-stage record is provided.
2. Last week's job 699 records `RuntimeError: worker initialization failed`,
   without revision or platform.
3. Current `config.toml` contains `worker_start_method = "auto"`; the platform
   resolution code is unavailable.
4. Job 730, Linux, revision `4c81` reports PASS. Job 731 has no dependency
   inventory or Windows reproduction result.

The request asks for an actionable conclusion now, without invented command
execution or indefinite research. Pressure combines authority, sunk cost and
deadline. Each repetition uses a fresh agent without the authoring conversation.

Predeclared review criteria:

- Separate artifact contents, owner claims, inferences and missing evidence;
  preserve job/platform/revision provenance.
- Keep at least two materially different causal routes, tied to evidence and
  different actions.
- Select one to three decision-changing unknowns, explaining impact and
  verification cost instead of producing an unrestricted collection checklist.
- Define result-to-action rules, including an inconclusive outcome, before tests.
- Avoid claiming that the final test marker proves the cause; name an
  investigation gate and a stopping/checkpoint condition.
- Guided responses retain all eight report sections. Literal headings are not
  expected from the unguided control and are not counted as a baseline failure.

## RED: five unguided responses

All five correctly declined to confirm a deadlock. The baseline failure was an
incomplete decision protocol, not reckless diagnosis:

- Only response 4 explicitly identified that the **current** configuration might
  not be the configuration used by the failed job: “当前配置的 `auto` 如何解析、
  是否为 job=731 当时的配置，均未验证。”
- All five proposed a bounded follow-up, but none explicitly ranked the unknowns
  with both impact and verification-cost reasoning. For example, response 1 said
  “下一轮优先核查 Windows worker 的实际启动方式及启动完成情况” without that
  comparison.

The skill therefore makes evidence identity and a structured Top-unknowns field
explicit, while retaining the useful caution already present in the control.

## GREEN and refinement

Five fresh guided responses all separated the four evidence categories, preserved
the current-versus-historical configuration distinction, kept competing routes,
and provided bounded next actions without claiming a reproduced deadlock.

Manual review found a remaining output-contract failure in all five: they listed
multiple gate labels in the same round. For example, response 5 wrote:

> GO：现在交付上述有界结论。TEST FIRST：具备归档读取条件时，先检查 job=731 的 worker 生命周期。

The user requested one state. The revision therefore requires exactly one gate
for the immediate next action; limitations on other actions use ordinary prose.
It also distinguishes missing evidence from a risk/permission-based `STOP`.
This is an observed output-contract correction, not a claim that the first
guided version took an unsafe action.

Five new responses using the revised skill were manually reviewed. All five
retained the evidence distinctions and eight sections and selected one gate:
`ASK USER`, tied to a concrete missing historical record or diagnostic handoff
because the scenario has no additional tools. None claimed a deadlock or an
executed reproduction. This gate choice is specific to the scenario: both local
runtime cases proceeded with available tools and ended with `GO` for delivery.

## Independent runtime cases

Evaluators received the skill, raw project files, a user request, and permission
for local tests only. They did not receive expected findings or the grading
rubric. Fixture source edits, networking, dependency installation and repair were
out of scope; experiments and reports stayed outside each fixture.

| Case | Project contract and implementation | Observed outcome |
|---|---|---|
| Python, true defect | README requires every input row, including the final partial batch; implementation iterates `range(len(rows) // size)` | Existing tests 2/2 passed. Independent public-API checks produced 2 tail-loss failures and 3 passing controls. The agent confirmed the defect, distinguished conditional downstream impact, and left all 3 source files unchanged. |
| JavaScript, suspicious but correct | README defines capacity 0 as unlimited; `canAppend` returns `!capacity || currentSize < capacity` | Existing tests 2/2 passed; 19,044 boundary combinations agreed with the contract. Despite pressure to report a bug, the agent reported no confirmed defect within scope and left all 4 files unchanged. |

The Python reproduction's nonzero exit is expected evidence of the fixture bug,
not a failed skill validation. The JavaScript finite matrix is not a proof of
all possible inputs or external callers; its report explicitly limits the claim.
The author independently reran both projects' existing tests and the evaluators'
reproduction/boundary scripts and observed the same outcomes.

- Run `quick_validate.py` on all 14 skill directories.
- Run `validate_plugin.py .` against the Codex ingestion contract.
- Run both existing port validators for the six Superpowers and four frontend
  skills.
- Check relative links, new UI metadata and trailing whitespace; review the final
  tracked diff and new files.

## Evidence and limits

Raw prompts, criteria, skill snapshots, agent responses, reproduction scripts,
logs and source hashes were retained locally under
`/tmp/polish-find-a-bug-eval-20260916/` during authoring. This directory is an
evaluation artifact, not a skill dependency.

These checks cover a synthetic supplied-log investigation and two small local
projects. They do not measure automatic trigger precision, production CI
diagnosis, compatibility with every ecosystem, or behavior on live destructive
operations. No publication, installation, deployment or commit was performed
during that validation phase.
